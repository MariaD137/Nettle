# Database

## Production: PostgreSQL on RDS

All Nettle application state — users, sessions, projects, scans, scan history,
billing anchors, scan usage, alerts, events and notification preferences —
lives in a PostgreSQL instance managed by `infra/lib/database-stack.ts`.

### Why not SQLite in the container

It was SQLite in the container, and that was the single largest production
blocker. App Runner replaces the container on every deployment and when it
scales, so the database file — and every account in it — was destroyed each
time the service was redeployed.

**App Runner has no persistent-filesystem option.** This is not a matter of
preference: `AWS::AppRunner::Service` exposes no volume, mount, file-system or
EFS property at all, so a durable SQLite file behind App Runner is not
expressible. The data has to live outside the container.

### Why PostgreSQL rather than DynamoDB

The access patterns are relational: `scanQuota` aggregates usage over a billing
period, `listScans` orders history per project, the Tier 2 detection rules
query an events time-window. Expressing those in DynamoDB means redesigning the
data model for no benefit at this size.

### Why a small RDS instance rather than Aurora Serverless v2

Identical application code either way. Aurora Serverless v2's 0.5 ACU floor
costs more than `db.t4g.micro` at this workload. The upgrade path stays open.

## Local development and tests: SQLite

`DATABASE_URL` selects the engine:

| `DATABASE_URL` | Engine | Used for |
|---|---|---|
| set | PostgreSQL | production |
| unset | SQLite at `NETTLE_DB_PATH` | local development, `npm test` |

Running the test suite needs no database server. **Production cannot silently
fall back**: `assertProductionPersistence()` refuses to start when
`NODE_ENV=production` and `DATABASE_URL` is unset, rather than booting onto
storage that is about to be discarded.

CI runs the suite against **both** engines (`.github/workflows/ci.yml`), because
they differ in ways that matter:

- PostgreSQL returns `COUNT(*)` as a bigint, which `pg` hands back as a
  **string**; queries use `CAST(... AS INTEGER)` and `Number()`.
- SQLite does not enforce declared foreign keys unless `PRAGMA foreign_keys` is
  on (it now is). PostgreSQL always does.
- Placeholders are written `?` and rewritten to `$1, $2, …` for PostgreSQL by
  `toPositionalPlaceholders()`.

## Schema migrations

Plain, versioned `.sql` files in `backend/src/db/migrations/`, applied in
filename order and recorded in `schema_migrations`. There is no ORM and none is
being introduced — the application is raw SQL over a thin driver.

The baseline is **dialect-neutral**: it runs unchanged on both engines. That is
possible because every primary key is a TEXT UUID generated by the application
and every timestamp is an ISO-8601 string generated in JS, so there is no
`AUTOINCREMENT`, no `rowid` dependence and no `CURRENT_TIMESTAMP`.

Guarantees:

- **versioned** — numeric filename prefix, ascending
- **idempotent** — an already-recorded version is skipped
- **transactional** — each migration commits as a unit or not at all
- **concurrency-safe** — a PostgreSQL advisory lock serialises App Runner
  instances that boot simultaneously
- **never destructive by default** — a migration containing `DROP TABLE`,
  `DROP COLUMN` or `TRUNCATE` is refused unless it carries an explicit
  `-- nettle:allow-destructive` marker

### Adding a migration

```bash
# backend/src/db/migrations/002_add_something.sql
```

Use dialect-neutral SQL (TEXT/INTEGER columns, `CREATE TABLE IF NOT EXISTS`).
Verify on both engines before merging — CI does this too.

### Applying migrations in production

Migrations run automatically at service start, before the HTTP listener opens,
so a broken migration fails the deployment rather than the first request that
touches the database. No separate migration step is required in the deploy
pipeline.

To apply them manually against RDS (for example from a bastion):

```bash
DATABASE_URL='postgresql://...' npx tsx -e \
  'import("./src/db").then(m => m.initializeDatabase())'
```

**Never** run a destructive command against the production database. There is
no `reset` command in this repository and none should be added.

## Migrating existing SQLite data

If a SQLite database holds real data, `backend/scripts/migrate-sqlite-to-postgres.ts`
copies it:

```bash
# Inspect first — writes nothing
DATABASE_URL='postgresql://...' \
  npx tsx scripts/migrate-sqlite-to-postgres.ts --source ./nettle.db --dry-run

# Then import
DATABASE_URL='postgresql://...' \
  npx tsx scripts/migrate-sqlite-to-postgres.ts --source ./nettle.db
```

It never writes to the source, refuses a target that already has users unless
`--force` is given, copies inside one transaction, and verifies row counts and
relationship integrity afterwards. It prints counts only — never password
hashes, session or reset token hashes, or Stripe identifiers.

**Current status: no production SQLite data exists to migrate.** The service
has never run durably in production — the container crashed at startup before
this work (the non-root user could not create the database file in the
root-owned `/app`). The tool exists for developer databases and for any
self-hosted instance.

## Legacy token-hash migration

Databases created before session and password-reset tokens were hashed keyed
those tables on the raw token. `backend/src/db/legacyTokenMigration.ts` rehashes
those rows in place, before the versioned migrations run, so introducing
hashing does not sign anyone out. SQLite only — PostgreSQL never had that
shape. Raw tokens are read solely to derive their hash and are never logged.

## Rate limiting

`rate_limit_buckets` (migration `002_rate_limits.sql`) backs the rate limiter
in `backend/src/middleware/rateLimit.ts`. It exists in this database rather
than a new Redis/DynamoDB resource because App Runner can run more than one
instance, and every instance already shares this same database — that is
enough to make the counters correct fleet-wide without adding a new AWS
resource for it. See the module's own comments for the atomic UPSERT this
relies on and why it fails open on a backing-store error.

The table is cleaned up by an in-process periodic sweep
(`startRateLimitCleanup`, called at boot in `index.ts`), not a scheduled AWS
job: its size is bounded by (distinct rate-limited scopes) × (distinct recent
callers), which stays small. This is a different situation from `events`
(Phase 12 retention, not yet implemented), whose volume scales with customer
traffic and needs a real scheduled job.

## Backups

- Automated backups, 14-day retention in production (1 day otherwise).
- Deletion protection on in production; `RemovalPolicy.RETAIN`, so tearing down
  the stack does not take the data with it.
- Storage encrypted at rest; storage autoscales 20 GB → 100 GB.
- Single-AZ at this size. Revisit Multi-AZ when load justifies the cost.
