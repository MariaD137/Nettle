# Nettle infra

Five stacks. Everything here has been verified with `cdk synth` — real,
valid CloudFormation — against no real AWS account, because none exists to
verify against. **Nothing has been deployed.** See "What's validated vs.
what isn't" below and `AWS_GITHUB_DEPLOYMENT.md` at the repo root for the
full deployment runbook and exactly what still requires a human with a real
AWS account.

- **Nettle-Network** — a VPC with public + private (with NAT egress)
  subnets and a single NAT gateway. This used to be zero-egress by design;
  it isn't anymore, because the app itself now makes real outbound calls
  (Stripe, SMTP, Twilio, outbound webhooks to customer URLs, git clones,
  SSRF-guarded scan-target fetches) that a fully isolated network would
  simply block. Inbound stays closed — nothing here is reachable from the
  internet directly.
- **Nettle-Api** — an ECR repo + a single App Runner service, egress routed
  through the VPC via a connector, `AutoScalingConfiguration` pinned to
  `minSize: 1, maxSize: 1` (still true — see below), and secrets pulled
  from AWS Secrets Manager at container startup via `runtimeEnvironmentSecrets`
  (never baked into the image, never in this repo). **`maxSize` stays
  capped at 1**: accounts/sessions/projects/scans/alerts are still
  persisted with `node:sqlite` on the single running container, not a
  shared database — a second concurrent instance would boot its own empty
  file and requests would silently see different data depending on which
  instance served them. Raise it the day a shared datastore actually
  replaces that, not before (see Nettle-Database).
- **Nettle-Database** — an RDS PostgreSQL instance (`db.t4g.micro`,
  single-AZ, encrypted storage), credentials generated by CDK straight into
  a new Secrets Manager secret — nobody, including whoever runs `cdk
  deploy`, ever sees or types the password. **Not part of the default
  deploy** (see `bin/app.ts`) and **not consumed by the application yet** —
  the backend's data layer still reads/writes SQLite exclusively; see
  `backend/src/db/postgres/README.md` for why that conversion is a
  deliberately separate, deferred piece of work. This stack exists so
  provisioning real Postgres is ready the moment that conversion happens.
- **Nettle-Frontend** — a private S3 bucket (no public access at all) +
  CloudFront distribution reaching it via Origin Access Control, with SPA
  routing (403/404 → `index.html`) so client-side routes survive a direct
  page load/refresh.
- **Nettle-CI** — a GitHub OIDC provider + a deploy role. Deliberately does
  **not** include permission to run `cdk deploy` or otherwise create/modify
  infrastructure — provisioning stays a human-run action with the
  deployer's own credentials. The role only gets the narrow, repeatable
  deploy-time actions CI actually performs: push images to the one ECR
  repo, sync built frontend assets to the one S3 bucket, invalidate the one
  CloudFront distribution. No AWS access keys are ever stored in GitHub.

## What's validated vs. what isn't

| Checked | How |
|---|---|
| All five stacks synthesize to valid CloudFormation | `cdk synth Nettle-Network Nettle-Api Nettle-Database Nettle-Frontend Nettle-CI` — clean, no errors |
| The App Runner service's secrets resolve to real Secrets Manager ARN references, not plaintext | Inspected the synthesized `Nettle-Api` template directly — `RuntimeEnvironmentSecrets` values are `Fn::Join` expressions building `arn:...:secret:nettle/app-secrets:<key>::`, never a literal value |
| RDS never has a plaintext password anywhere in the template | Inspected the synthesized `Nettle-Database` template — the secret is `GenerateSecretString` (CDK/CloudFormation generates it at deploy time) and the DB instance references it via `{{resolve:secretsmanager:...}}`, a dynamic reference that never appears as a literal |
| The CI role's new S3/CloudFront permissions resolve to the actual bucket/distribution ARNs, correctly, across accounts | Caught and fixed a real bug this way: an early version string-interpolated `env.account` (`undefined` in environment-agnostic synthesis) directly into the CloudFront ARN. Now built with `Stack.formatArn()`, confirmed in the synthesized template to resolve via `Ref: AWS::AccountId` |
| Docker image build | **Not run** — no Docker daemon available in this sandbox |
| Actual `cdk deploy` / any real AWS resources | **Not run** — needs a real AWS account and credentials, which are never pasted into a chat session (see the security constraints in `AWS_GITHUB_DEPLOYMENT.md`) |

## Cost notes (estimates, not sourced pricing — check AWS's current pricing page)

- App Runner at the smallest tier (0.25 vCPU / 0.5 GB), running
  continuously: roughly $10-25/month.
- One NAT gateway: roughly $32-45/month plus data processing — this is now
  the largest fixed cost in this stack, a direct consequence of the app
  needing real internet egress (see Nettle-Network above). There is no
  cheaper way to give a VPC-connected App Runner service internet access
  short of removing the VPC connector entirely, which would also remove
  the path to a VPC-private RDS instance.
- RDS `db.t4g.micro`, single-AZ, 20GB: roughly $15-25/month, if/when
  `Nettle-Database` is actually deployed (it isn't part of the default
  deploy today).
- S3 + CloudFront: a few cents to a few dollars a month at low traffic.
- ECR image storage: a few cents/month at this scale.
- VPC, subnets, security groups, IAM, the OIDC provider, Secrets Manager
  secret storage: Secrets Manager charges roughly $0.40/secret/month;
  everything else here is no charge.

Rough total with the default deploy (network + API + frontend + CI, no
RDS): $45-75/month. Add ~$15-25/month if `Nettle-Database` is deployed too.

## What's deliberately not here yet

- **Cognito.** Auth is real (email/password, scrypt-hashed, opaque session
  tokens, email verification) but hand-rolled rather than Cognito-backed —
  revisit if there's a concrete reason (social login, SSO for enterprise
  customers) to want a managed identity provider instead.
- **A queue between Tier 2 intake and detection** (Kinesis, per earlier
  architecture notes) — `POST /api/events` runs detection inline on the
  request today. Fine at low volume; add the queue when there's real
  traffic to justify it.
- **True per-scan sandboxing** — today the whole API service is
  network-isolated (from the internet, inbound), which is real but
  coarse-grained: one large or malicious upload still runs in the same
  process as everything else. Per-job ephemeral isolation (a Fargate task
  per scan, or a service like e2b/Modal built for running untrusted code)
  is the next real hardening step once there's actual multi-tenant traffic
  to protect against.
- **Multi-AZ / redundant NAT gateways, RDS Multi-AZ, CloudFront additional
  origins/behaviors** — all deliberately single-AZ/single-NAT for cost at
  this stage. Add redundancy once there's real paying traffic whose uptime
  is worth the doubled NAT/RDS cost.
