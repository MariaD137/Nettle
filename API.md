# Nettle API Reference

Base URL: the backend's own address — `http://localhost:8080` in
development (see `backend/README.md`), whatever your deployment sets
`PORT`/its public URL to otherwise. There is no separate versioned path;
all routes are under `/api/*` (plus a bare `/health`).

This document is generated by hand against the actual route files in
`backend/src/routes/` — every endpoint, request shape, and response shape
below is real, not aspirational. If it drifts from the code again, trust
the code.

## Authentication

Two independent schemes are in use, for two different kinds of caller:

| Scheme | Header | Identifies | Used by |
|---|---|---|---|
| Session token | `Authorization: Bearer <token>` | A logged-in user | The dashboard and CLI, for everything account-scoped |
| Project API key | `X-Nettle-Api-Key: <key>` | A single project | Scanning (to associate/bill a scan without logging in) and event ingestion |

- Session tokens are issued by `POST /api/auth/signup` or `POST /api/auth/login` and never expire client-side — they're checked server-side against the `sessions` table (see `GET /api/auth/sessions` / revocation endpoints below).
- A project's default API key is shown at creation (`POST /api/projects`) and on rotation (`POST /api/projects/:id/rotate-key`); it is not otherwise retrievable through the API. Additional named/scoped keys can be created via `POST /api/projects/:id/api-keys` (see the API key management section below) — that response is likewise the only place the full value is ever returned.
- A key that's been revoked (or, for scoped keys, doesn't carry the scope a route requires) fails authentication immediately — treated identically to an unknown key. Every successful authentication updates that key's `lastUsedAt`.
- `POST /api/events` **requires** `X-Nettle-Api-Key` (scope: `events`) — there is no session-based way to ingest events.
- `POST /api/scans`, `POST /api/scans/repo`, `POST /api/scans/url`, and their async `/api/scans/jobs/*` equivalents accept `X-Nettle-Api-Key` **optionally** (scope: `scan`), to attribute/bill an otherwise-anonymous scan to a project. Note the inconsistency in the codebase itself: the upload routes read it from the header, while `/repo` and `/url` additionally accept an `apiKey` field in the JSON body — both work, header and body aren't unified.
- Routes with no auth at all: `GET /health`, `GET /api/projects/:id/badge.svg`, `GET /api/projects/:id/badge.json` (deliberately public — see their section below), and `POST /api/billing/webhook` (authenticated instead by a Stripe HMAC signature).

## Rate limiting

| Limiter | Limit | Applies to |
|---|---|---|
| `apiRateLimit` | 500 req / 60s per IP | Every route (mounted globally, right after `/health`) |
| `scanRateLimit` | 30 req / 60s per IP | `/api/scans/*` and `/api/scans/jobs/*` (stacks with the global limiter above) |
| `publicRateLimit` | 100 req / 5min per IP | `/api/events`, `/api/projects/:id/badge.*` |
| Auth-specific limiter | 15 req / 15min per IP+path | `/api/auth/signup`, `/login`, `/forgot-password`, `/reset-password` (stacks with the global limiter) |

A 429 response is `{ "error": "...", "retryAfter": <seconds> }` (the
auth-specific limiter omits `retryAfter` but sets the same
`X-RateLimit-*`/`Retry-After` response headers). There is no per-webhook
rate limit currently enforced despite a `webhookRateLimit` function
existing in the codebase — it's defined but not wired into any route, so
don't rely on it.

All three limiters above are keyed **per IP, not per user**, despite
`apiRateLimit`'s own code comment claiming "per authenticated user": the
key lookup reads `req.user?.id`, but auth middleware only ever sets
`req.userId` (no route in the codebase sets `req.user`), so that lookup
is always `undefined` and every limiter falls back to IP. In practice
this means every request sharing an egress IP (a NAT, a corporate proxy,
multiple accounts on one machine) shares one rate-limit bucket — worth
knowing if you're building against this, and worth fixing in the
middleware itself at some point.

## Error shape

Every failure response is `{ "error": "human-readable message" }`. Two
routes extend that shape with machine-readable fields for the frontend to
branch on without string-matching the message:

- `402` from `requireSubscription` (all of `projects.routes.ts`, `POST /api/scans/repo`): `{ error, subscriptionRequired: true, plan, subscriptionStatus }`
- `402` from an exhausted scan quota (`POST /api/scans`, `/repo`, `/url`, and their job equivalents): `{ error, quotaExceeded: true, limit, used, remaining: 0, periodEnd }`

Common status codes: `400` bad input, `401` missing/invalid session,
`402` payment/quota required, `403` — used only by `POST /api/projects`
when the plan's project-count limit is reached, `404` not found (or not
yours — ownership failures return 404, not 403, almost everywhere; the
two exceptions are noted per-route below), `413` upload too
large/decompression-bomb-shaped, `422` couldn't complete (e.g. a scan
target that failed to clone/extract), `429` rate limited, `500` unhandled
server error.

## Object shapes referenced below

To avoid repeating these in every endpoint:

**User** — `{ id, email, plan, stripeCustomerId, subscriptionStatus, billingAnchor, onboardingCompletedAt, createdAt }`. Never includes the password hash.

**Project** — `{ id, userId, name, apiKey, url, repoUrl, repoBranch, hasRepoAccessToken, description, environment, archivedAt, createdAt }`. `apiKey` is included on every project response — there's no restricted view that omits it, so treat any endpoint returning a `Project` as sensitive.

**ScanReport** (the actual scan output — see `backend/src/scanner/types.ts`) — `{ scannedAt, target, scanType, scannerVersion, semgrepVersion, score, scoreConfidence, status, access, environment, findings: Finding[], passed, checkResults?, attackChains?, summary: { critical, high, medium, low, info, clear } }`. A `Finding` is `{ severity, category, title, detail, file, line, remediation, dependencyPaths?, ruleId?, codeContext? }`. `access` (see below) is only present when the report was trimmed for a free/unauthenticated caller.

**ScanAccess** — `{ tier: "preview"|"full", fullReport: boolean, totalFindings, visibleFindings, lockedFindings, message }`. A free-tier or anonymous scan gets `findings` truncated to a preview slice; `access.message` explains what's hidden.

**StoredScan** (a scan as persisted against a project — `GET /api/projects/:id/scans` etc.) — `{ id, projectId, scannedAt, score, criticalCount, cautionCount, clearCount, status, scannerVersion, semgrepVersion, report: ScanReport }`. `scannerVersion`/`semgrepVersion` are `null` for scans recorded before that tracking existed.

**Alert** — `{ id, projectId, occurredAt, severity: "critical"|"high"|"medium"|"low", rule, message, status: "new"|"acknowledged"|"resolved"|"false_positive" }`.

**BadgeState** — `{ status, label, lastScannedAt, score }`.

**QuotaState** — `{ limit, used, remaining, periodStart, periodEnd, exhausted }`.

**CustomRule** — `{ id, project_id, name, description?, pattern_type: "exact"|"regex"|"threshold"|"combination", pattern_value, weight, severity: "critical"|"high"|"medium"|"low", enabled, version, created_by, created_at, updated_at }`. Note: snake_case — this router predates the camelCase convention used everywhere else and was never normalized.

**WebhookConfig** — `{ id, project_id, service: "slack"|"pagerduty"|"splunk"|"datadog"|"generic", webhook_url, is_active, event_types: string[], created_at, updated_at }` (also snake_case).

## Health

### `GET /health`
No auth. `{ status: "ok", timestamp }`.

## Auth (`/api/auth/*`)

All under the 15-req/15-min auth limiter where noted.

### `POST /api/auth/signup` *(rate-limited)*
Body: `{ email, password }` (password ≥ 8 chars). → `201 { token, user }`. `409` if the email's already registered.

### `POST /api/auth/login` *(rate-limited)*
Body: `{ email, password }`. → `{ token, user }`. `401` on bad credentials.

### `POST /api/auth/logout`
Auth required. Destroys the calling session. → `204`.

### `GET /api/auth/me`
Auth required. → `{ user }`.

### `POST /api/auth/onboarding/complete`
Auth required. Marks onboarding done. → `{ user }`.

### `POST /api/auth/forgot-password` *(rate-limited)*
Body: `{ email }`. Always → `{ message }` regardless of whether the email is registered (doesn't leak account existence). The reset token itself is only logged server-side (`console.log`) — there's no email delivery wired up yet.

### `POST /api/auth/reset-password` *(rate-limited)*
Body: `{ token, password }`. → `{ message }`. `400` if the token is invalid/expired or the password's too short.

### `POST /api/auth/change-password`
Auth required. Body: `{ currentPassword, newPassword }`. → `{ message }`. `401` if `currentPassword` is wrong.

### `PATCH /api/auth/email`
Auth required. Body: `{ email, password }` — password confirms the change. → `{ user }`. `409` if the new email's taken.

### `GET /api/auth/sessions`
Auth required. → `{ sessions: SessionInfo[] }` where `SessionInfo` is `{ tokenPrefix, createdAt, expiresAt, current }` — `tokenPrefix` is the first 8 characters plus `…`, never the full token.

### `DELETE /api/auth/sessions/:tokenPrefix`
Auth required. Revokes one session by its prefix (from the list above). → `204`, or `404` if no matching session.

### `POST /api/auth/sessions/revoke-all`
Auth required. Revokes every session for the account **including the one making the request**, then issues a fresh token. → `{ token, message }` — the caller must swap in the new token immediately.

### `DELETE /api/auth/account`
Auth required. Body: `{ password }`. Permanently deletes the account and everything under it. → `204`, or `401` if the password's wrong.

## Projects (`/api/projects/*`, `/api/overview`)

Every route in this section requires **both** `requireAuth` and
`requireSubscription` (see the 402 shape above) — there is no free-tier
access to project management, only to a one-off anonymous scan.

### `POST /api/projects`
Body: `{ name, url?, repoUrl?, repoBranch?, description?, environment? }`. → `201 Project`. `403` if the plan's project-count limit is reached (free: 3, tier1: 10, tier2: 50).

### `GET /api/projects`
Query: `?includeArchived=true` to include archived projects. → `{ projects: Project[] }`.

### `GET /api/projects/:id`
→ `{ project, badge: BadgeState, latestScan: StoredScan | null, alertCounts: { new, acknowledged, resolved, false_positive } }`.

### `PATCH /api/projects/:id`
Body: any subset of `{ name, url, repoUrl, repoBranch, description, environment, repoAccessToken }`. `repoAccessToken` is encrypted at rest; an empty string clears it, omitting the field leaves it untouched. → updated `Project`.

### `DELETE /api/projects/:id`
→ `204`. Cascades to the project's scans, alerts, etc.

### `POST /api/projects/:id/archive` / `POST /api/projects/:id/restore`
→ updated `Project`.

### `POST /api/projects/:id/rotate-key`
Rotates the project's **default** key (see multi-key management below) and mirrors the new value into this legacy field — invalidates the old value immediately. → updated `Project` (with the new key).

### API key management (`/api/projects/:id/api-keys*`)

A project has one key per the legacy field above, plus any number of
additional named, scoped, independently revocable keys — a real child
table (`api_keys`), not just fields on `Project`. Every project's very
first key (seeded at creation, or backfilled for older projects) is
marked as its **default** key and stays mirrored into `Project.apiKey`
and the legacy rotate-key endpoint above, so nothing that already reads
`project.apiKey` breaks. `StoredApiKey` is `{ id, projectId, name, key, scopes: ("scan"|"events")[], isDefault, lastUsedAt, revokedAt, createdAt }`.

Scopes gate what a key can actually do: `POST /api/events` requires the
`events` scope, and `POST /api/scans` / `/repo` / `/url` (and their
`/api/scans/jobs/*` equivalents) require `scan` to attribute a scan to
the project — a key missing the needed scope is treated exactly like an
unknown key (falls back to anonymous/unattributed, not a hard failure,
except at `/api/events` where a key is mandatory so it's a `401`).

- **`POST /api/projects/:id/api-keys`** — Body: `{ name, scopes? }` (`scopes` defaults to both if omitted/invalid). → `201 { apiKey: StoredApiKey }` with the **full, real key value** — the only response that ever includes it.
- **`GET /api/projects/:id/api-keys`** — → `{ apiKeys: StoredApiKey[] }`, `key` masked on every entry (e.g. `nettle_a1b2…c3d4`).
- **`PATCH /api/projects/:id/api-keys/:keyId`** — Body: any subset of `{ name, scopes }`. → `{ apiKey }` (masked).
- **`POST /api/projects/:id/api-keys/:keyId/rotate`** — Regenerates just this key's secret, old value stops working immediately. → `{ apiKey }` with the full new value (once). Rotating the default key also updates `Project.apiKey`.
- **`POST /api/projects/:id/api-keys/:keyId/revoke`** — Immediate, idempotent, permanent — there's no un-revoke. Doesn't delete the row; name/scopes/lastUsedAt stay visible as history. → `{ apiKey }` (masked) with `revokedAt` set.

### `GET /api/projects/:id/alerts`
→ `{ project: { id, name }, alerts: Alert[] }`.

### `PATCH /api/projects/:id/alerts/:alertId`
Body: `{ status }` (one of `new`/`acknowledged`/`resolved`/`false_positive`). → `{ alert }`.

### `GET /api/projects/:id/alerts/analytics`
Query: `?hours=` (default 24, clamped to 1–720). Aggregates the project's own alerts within that window — nothing ML-derived, purely counting/grouping stored alert rows. → `{ analytics: AlertAnalytics }` where `AlertAnalytics` is:
- `timeline: { hour, count, bySeverity: { critical, high, medium, low } }[]` — one zero-filled entry per hour in the window (oldest first), so a quiet hour shows `count: 0` rather than being omitted.
- `topAttackTypes: { label, count }[]` — alert `rule` values collapsed back to their base attack type (e.g. `suspicious-path-203.0.113.5` → `suspicious-path`), ranked by count.
- `topEndpoints: { label, count }[]` — the request path named in each alert's message, parsed from the quoted substring `detection.ts` always includes when a specific path triggered the rule. Alerts with no single associated path (`brute-force`, `high-request-rate`, `custom-rule-*`) aren't attributed to any endpoint.
- `topCountries: { label, count }[]` — the ISO country code for the IP named in each alert (from the rule-name suffix or the message text), resolved via a bundled offline GeoIP database (`geoip-lite`, no network call). Alerts with no single attributable IP (`credential-stuffing-*`, `custom-rule-*`) or an unresolvable IP (private/reserved ranges) are excluded, not bucketed into a fake "unknown".

### Detection thresholds (`/api/projects/:id/detection-settings*`)

Per-project overrides for the built-in `detection.ts` rule thresholds (brute-force failed-auth count, high-request-rate count, credential-stuffing distinct-IP count). No override row means the built-in defaults (5, 50, 5) apply — every project behaves identically until someone customizes it. `DetectionSettings` is `{ projectId, bruteForceThreshold, highRequestRateThreshold, credentialStuffingMinIps, updatedAt }` (`updatedAt: null` means still on defaults).

- **`GET /api/projects/:id/detection-settings`** → `{ settings: DetectionSettings }`.
- **`PATCH /api/projects/:id/detection-settings`** — Body: any subset of `{ bruteForceThreshold, highRequestRateThreshold, credentialStuffingMinIps }` (each must be a positive integer; invalid values are ignored and the previous value is kept, not rejected outright). → `{ settings }`.
- **`POST /api/projects/:id/detection-settings/reset`** — Removes the override, reverting to defaults. → `{ settings }`.

### `GET /api/projects/:id/scans`
→ `{ project: { id, name }, scans: StoredScan[] }`, newest first.

### `GET /api/projects/:id/scans/compare`
Query: `?from=<scanId>&to=<scanId>` — both optional; defaults to the two most recent scans (previous vs. latest). `400` if the project has fewer than 2 scans. → 
```
{
  from: { id, score, scannedAt }, to: { id, score, scannedAt },
  scoreDelta,
  fixed, new, remaining,              // counts
  fixedFindings, newFindings, remainingFindings,  // full Finding[] for each
  changeIntelligence                  // see scanner/changeIntelligence.ts
}
```
Finding identity for the diff is `category::title::file` — no hash/ID involved.

### `GET /api/projects/:id/findings`
→ `{ findingStatuses: StoredFindingStatus[], findingHistory: FindingHistoryEntry[] }`. `StoredFindingStatus` is `{ id, projectId, findingHash, status, notes, createdAt, updatedAt }`; `FindingHistoryEntry` is `{ findingHash, firstSeenAt, lastSeenAt }`. `findingHash` is a stable per-finding identity — see `hashFinding()` in `patrol/findingStatuses.ts` — computed the same way both here and independently in the frontend.

### `PATCH /api/projects/:id/findings/:findingHash`
Body: `{ status, notes? }` (`status` one of `open`/`in_progress`/`resolved`/`false_positive`/`accepted_risk`). Omitting `notes` leaves existing notes untouched (it doesn't clear them). → `{ findingStatus }`.

### `GET /api/projects/:id/scans/:scanId/export`
Downloads the full `ScanReport` as JSON (`Content-Disposition: attachment`). → raw `ScanReport` body, not wrapped in an envelope.

### `GET /api/overview`
Cross-project dashboard summary for the whole account. → 
```
{
  quota: QuotaState,
  totalProjects, totalCriticalFindings, totalHighFindings, totalNewAlerts,
  latestScore, latestScanAt,
  projects: [{ id, name, environment, badge, latestScore, lastScannedAt, newAlerts }]
}
```

## Scanning — synchronous (`/api/scans/*`)

The original, blocking scan routes: the response *is* the finished
report. Used by the CLI and any direct API integration, which expect one
round trip. `POST /api/scans` allows anonymous callers (`optionalAuth`);
the other two require a session.

### `POST /api/scans`
`multipart/form-data`, field `codebase` = a `.zip` (max 25MB). Optional `X-Nettle-Api-Key` header to associate/bill the scan to a project. → `ScanReport`, trimmed to the caller's plan via `access` if not a full-tier account. `400` for a non-zip or missing file, `413` for an oversized/bomb-shaped archive, `422` for any other extraction failure.

### `POST /api/scans/repo`
Auth + subscription required. Body: `{ repoUrl, branch?, apiKey? }` — `repoUrl` must be an `https://` GitHub/GitLab/Bitbucket URL. If `apiKey` identifies a project with a stored (encrypted) repo access token, that token is used to clone a private repo; otherwise only public repos work. → `ScanReport`. `404` if the repo can't be found, `400` for a bad branch.

### `POST /api/scans/url`
Auth required (not subscription). Body: `{ url, confirmed: true, apiKey? }` — `confirmed` must be explicitly `true`; this is a black-box external scan (headers/TLS/exposed paths — never source code) and Nettle's own infrastructure makes the outbound request, so it requires login and explicit authorization. SSRF-guarded: private/reserved/loopback targets are rejected with `400`. → `ScanReport` with `scanType: "URL"`.

All three share the same quota gate (`402` with `quotaExceeded: true` — see Error shape above) and the same `applyScanAccess()` plan-trimming.

## Scanning — async jobs (`/api/scans/jobs/*`)

The web dashboard's counterpart to the routes above: returns immediately
with a job ID, runs the scan in a background `worker_thread` with real
step-by-step progress and a concurrency-limited queue, instead of
blocking the request. Functionally equivalent output; always requires
auth (no anonymous jobs).

### `POST /api/scans/jobs/upload`
Same `multipart/form-data` shape as `POST /api/scans`. → `202 { jobId }`.

### `POST /api/scans/jobs/repo`
Same body shape as `POST /api/scans/repo`. → `202 { jobId }`.

### `GET /api/scans/jobs/:jobId`
Poll for status. → a `ScanJob`:
```
{
  id, status: "queued"|"running"|"completed"|"failed"|"cancelled",
  source: "upload"|"repo"|"url",
  steps: [{ id, label, status: "pending"|"running"|"done" }],
  createdAt, startedAt, finishedAt,
  report: ScanReport | null,       // present once completed, plan-trimmed
  error: string | null,
  friendlyError?: string,          // present alongside error when status is "failed"
  queuePosition: number | null,
}
```
`404` if the job doesn't exist or belongs to a different account.

### `POST /api/scans/jobs/:jobId/cancel`
→ `204`, or `409` if the job already finished/was already cancelled.

## Events (`/api/events`)

### `POST /api/events`
Requires `X-Nettle-Api-Key` (no session-token option). Body: `{ ip, method, path, statusCode, userAgent? }`. Records a Tier 2 monitoring event and runs anomaly/rule detection against it inline. → `202 { recorded: true, newAlerts: Alert[] }`. `401` for a missing/invalid key.

## Badge (`/api/projects/:id/badge.*`)

Deliberately public, no auth — meant to be embedded with a plain
`<img>` tag on a customer's own site. The project ID isn't treated as a
secret; it only reveals pass/fail badge state, not any account or scan
detail.

### `GET /api/projects/:id/badge.svg`
→ `image/svg+xml`, `Cache-Control: no-cache, max-age=0`. `404` (empty body) if the project doesn't exist.

### `GET /api/projects/:id/badge.json`
→ `BadgeState` as JSON, same cache header. `404 { error }` if not found.

## Billing (`/api/billing/*`)

### `POST /api/billing/checkout-session`
Auth required. Body: `{ plan: "tier1"|"tier2" }`. Creates a Stripe Checkout session. → `{ url }` to redirect the browser to. `503` if Stripe isn't configured.

### `POST /api/billing/webhook`
Not auth'd by token — verified by Stripe's HMAC signature (`Stripe-Signature` header) against the raw request body, which is why this router is mounted *before* `express.json()` in `index.ts`. Handles `checkout.session.completed`, `customer.subscription.updated`, `customer.subscription.deleted`. → `{ received: true }`.

## Custom rules (`/api/custom-rules/:projectId/*`)

Auth required on every route; ownership check returns **403** here (not
404, unlike the rest of the API) when the project isn't yours.

### `POST /api/custom-rules/:projectId`
Body: `{ name, description?, pattern_type, pattern_value, weight?, severity?, enabled? }` (`pattern_type` one of `exact`/`regex`/`threshold`/`combination`; `weight` defaults 50, `severity` defaults `medium`). → `201 CustomRule`.

### `GET /api/custom-rules/:projectId`
Query: `?enabledOnly=true`. → `{ rules: CustomRule[] }`.

### `GET /api/custom-rules/:projectId/:ruleId`
→ `CustomRule`, or `404`.

### `PATCH /api/custom-rules/:projectId/:ruleId`
Body: any subset of the create fields. → updated `CustomRule`.

### `DELETE /api/custom-rules/:projectId/:ruleId`
→ `{ deleted: true }`.

### `POST /api/custom-rules/:projectId/:ruleId/test`
Body: `{ events: [...] }` (1–10,000 events). Runs the rule against sample events without persisting anything. → rule-test result (see `patrol/customRules.ts#testRule`).

### `GET /api/custom-rules/:projectId/:ruleId/versions`
→ `{ versions }` — the rule's edit history.

### `GET /api/custom-rules/:projectId/:ruleId/test-results`
Query: `?limit=` (default 10). → `{ results }` — past test runs.

## Analytics (`/api/analytics/:projectId/*`)

Auth required; ownership check also returns **403** (same pattern as
custom rules, not the 404 the rest of the API uses).

### `POST /api/analytics/:projectId/calculate-baselines`
Body: `{ hoursBack? }` (default 24). Recomputes ML baseline stats from recent events. → baseline result, or `400 { error }` if there isn't enough data.

### `GET /api/analytics/:projectId/baselines`
Query: `?metric=&period=&hour=`. → `{ baselines: [{ id, metric_name, hour_of_day, value, std_dev, percentile_50, percentile_95, percentile_99, updated_at }] }`.

### `GET /api/analytics/:projectId/anomalies`
Query: `?limit=` (default 50), `?score_min=` (default 0.7). → `{ anomalies }`.

### `GET /api/analytics/:projectId/model-status`
→ `{ model_type, is_active, trained_at, training_samples, accuracy }`, or a not-yet-trained placeholder (`{ isolation_forest: { is_active: false, reason }, lstm: { is_active: false, reason } }`) if nothing's been trained yet.

### `GET /api/analytics/:projectId/dashboard`
Query: `?timeframe=` (currently informational only — the query always looks at the last 24h regardless of this value). → `{ metrics: { request_count, error_rate, request_baseline, error_baseline }, anomalies, model_status }`.

## Integrations / webhooks (`/api/projects/:projectId/webhooks/*`)

Auth required; ownership check returns 404 (consistent with the general
API convention, unlike custom-rules/analytics above).

### `POST /api/projects/:projectId/webhooks`
Body: `{ service, webhook_url, event_types: string[] }` (`service` one of `slack`/`pagerduty`/`splunk`/`datadog`/`generic`). → `201 WebhookConfig`.

### `GET /api/projects/:projectId/webhooks`
→ `WebhookConfig[]` (a bare array, not wrapped in an envelope — inconsistent with most other list endpoints, which return `{ items: [...] }`).

### `GET /api/projects/:projectId/webhooks/:webhookId`
→ `WebhookConfig`, or `404`.

### `PATCH /api/projects/:projectId/webhooks/:webhookId`
Body: any subset of `{ webhook_url, event_types, is_active }`. → updated `WebhookConfig`.

### `DELETE /api/projects/:projectId/webhooks/:webhookId`
→ `204`.

### `POST /api/projects/:projectId/webhooks/:webhookId/test`
Sends a real test delivery to the configured URL with `event_type: "test_event"`. → `{ message: "Test webhook sent successfully" }`.

### `GET /api/projects/:projectId/webhooks/:webhookId/events`
Query: `?limit=` (default 50). → `WebhookEvent[]` (also a bare array), each `{ id, webhook_id, event_type, payload, status: "pending"|"sent"|"failed"|"retrying", attempt_count, last_error?, created_at, sent_at? }`.

**Real event types** a webhook can be subscribed to (from the actual call sites, not aspirational): `scan.completed` (fires from every recorded scan — `recordScan()` — with `{ scan_id, project_id, status, score, critical_count, caution_count, clear_count, scanned_at }`, delivered generically to every active webhook subscribed to it regardless of service), `incident_alert`, `incident_resolved` (PagerDuty), `anomaly_alert` (Datadog/Slack/Splunk), `metric_event`, `platform_event`, `log_event` (Datadog/Splunk), `notification` (Slack), and `test_event` (only from the `/test` endpoint above). A webhook only fires for event types listed in its own `event_types`.

## What changed from the previous version of this document

The previous `API.md` had drifted significantly from the code: it
documented `GET /api/scans/:scanId` and `GET /api/scans/:scanId/findings`
(neither exists), gave every analytics and custom-rules endpoint the
wrong path (missing the required `:projectId` segment), invented a
`scan_complete` webhook event type that's never actually sent, omitted
this account's 13 auth endpoints beyond signup/login/me, and claimed a
fictional `https://api.nettle.app` base URL. This rewrite was produced by
reading all 11 route files directly rather than extending the old one.

Since that rewrite, a real `scan.completed` webhook event was added
(`recordScan()` in `backend/src/patrol/scans.ts`) — note the dot, not the
old doc's invented underscore-separated `scan_complete`, which still does
not exist and never fires.
